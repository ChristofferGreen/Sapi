Feedback-Directed Optimization of Critical Execution Paths

Structure: wiki

Evidence from profile-guided compilation

The profile-guided source describes weighted flow graphs with execution counts on basic blocks and taken counts on control-flow arcs, then uses trace selection and tail duplication to form super-blocks from frequently executed traces. Its effectiveness claims emphasize eliminating entries into the middle of traces and optimizing the most frequently executed loop path, with benchmark speedups and controlled code growth.

Evidence from WCET-aware compilation

The WCC source frames timing improvement around the worst-case execution path: reducing a noncritical block may leave global WCET unchanged, so optimizations use WCEP membership, execution frequencies, cache misses, spill-code data, and other back-annotated facts. Register allocation, scratchpad allocation, and composed optimization sequences then reduce WCET by prioritizing the statically critical path.

Shared concept

Several compiler strategies become more effective when they focus optimization effort on the execution paths that matter most. Profile-guided classic optimization identifies frequently executed paths using weighted flow graphs and converts them into super-blocks, while WCC uses static WCET analysis to identify the worst-case execution path and direct transformations toward timing-critical regions. The common concept is path-sensitive feedback: measured hotness and statically derived worst-case criticality are different evidence sources for deciding where optimizations should be concentrated.

Why this supports a topic page

This topic can compare dynamic hot-path optimization with static worst-case-path optimization without treating them as the same problem. Both sources support a broader page about compiler feedback loops that select regions, reshape control flow or placement, and trade local costs such as code size or spill code against path-level performance goals.

Claims Used by This Topic

  • Weighted graphs expose hot paths

    Weighted flow graphs expose hot paths by attaching execution counts to basic blocks and taken counts to control-flow arcs.

  • Super-blocks isolate hot paths

    Super-blocks represent frequently executed paths as linear basic-block sequences that can only be entered at the first block but may exit from any block.

  • Tail duplication forms super-blocks

    Trace selection followed by tail duplication converts frequently executed traces into super-blocks by removing control-flow entries into the middle of a trace.

  • Effectiveness has two mechanisms

    The major effectiveness mechanisms are eliminating entries into the middle of traces and optimizing the most frequently executed loop path.

  • Profile optimization speeds benchmarks

    On the benchmark suite, profile-based super-block optimizations averaged a 1.15 speedup over the prototype compiler's globally optimized code.

  • WCEP governs WCET savings

    Static WCET reduction depends on optimizing the worst-case execution path, because reducing a noncritical path or a local block can leave the global WCET unchanged or only partly reduced.

  • Back annotation enables optimization

    WCC’s back-annotation raises assembly-level WCET information to source-level ICD-C structures, enabling source-level optimizations to use WCET, WCEP membership, execution frequencies, cache misses, code size, and...

  • Register allocation protects WCEP

    WCET-aware register allocation lowers WCET by avoiding spill code on the WCEP, even when this increases total spill code or text size outside the critical path.

  • Optimizations compose strongly

    The WCC optimizations compose: applying register allocation, code and data scratchpad allocation, and procedure positioning to matmult reduces WCET by more than 70 percent relative to WCC -O2.
