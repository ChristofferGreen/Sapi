Claims Referencing This Source

  • Classic optimizations fit super-blocks

    Classic scalar optimizations can be reformulated to operate on super-blocks and super-block loops rather than only on traditional basic blocks or whole loops.

  • Profiles guide classic optimizations

    Execution profiles integrated into an optimizing C compiler can guide classic optimizations toward the program regions that run most often.

  • Profile optimization speeds benchmarks

    On the benchmark suite, profile-based super-block optimizations averaged a 1.15 speedup over the prototype compiler's globally optimized code.

  • Profile optimizations complement convention

    Profile-based classic optimizations are intended to complement conventional optimizations rather than replace them.

  • Super-blocks isolate hot paths

    Super-blocks represent frequently executed paths as linear basic-block sequences that can only be entered at the first block but may exit from any block.

  • Duplication exposes producer relationships

    Tail duplication creates additional optimization opportunities because it can make an earlier operation the sole producer of operands used later in a hot path.

  • Benchmarks use separate inputs

    The experiments used separate profiling inputs and performance-measurement inputs across realistic C application programs.

  • Implementation cost is modest

    The implementation cost of profile-based classic optimization was modest relative to the existing global optimizer.

  • Effectiveness has two mechanisms

    The major effectiveness mechanisms are eliminating entries into the middle of traces and optimizing the most frequently executed loop path.

  • Code expansion stays controlled

    The profile-based transformations controlled executable size growth, averaging 1.07 relative size compared with globally optimized programs.

  • Tail duplication forms super-blocks

    Trace selection followed by tail duplication converts frequently executed traces into super-blocks by removing control-flow entries into the middle of a trace.

  • Weighted graphs expose hot paths

    Weighted flow graphs expose hot paths by attaching execution counts to basic blocks and taken counts to control-flow arcs.

  • Aestimo compares workload performance

    Aestimo evaluates performance effects by running each feedback-directed binary on every workload input five times and comparing arithmetic and normalized geometric runtime summaries against the static binary.

  • Aestimo isolates FDO transformations

    Aestimo isolates individual feedback-directed optimization transformations by recording profile-guided decisions for one optimization and recompiling so that only that optimization reuses the logged decisions.

  • Ansor finds unreachable programs

    Ansor can find high-performance tensor programs outside the search spaces covered by existing search-based frameworks.

  • Scheduling reduces search time

    Ansor can match AutoTVM's performance with much less search time by jointly optimizing subgraphs and prioritizing important ones.

  • Ansor improves DNN execution

    Ansor improves end-to-end DNN execution performance on Intel CPU, ARM CPU, and NVIDIA GPU by up to 3.8x, 2.6x, and 1.7x relative to the best evaluated alternatives.

  • Benchmarks favor Ansor

    Ansor outperforms existing search frameworks and manual libraries on single-operator and subgraph benchmarks across evaluated cases.

  • Cost model predicts throughput

    Ansor's learned cost model predicts tensor-program throughput accurately enough to guide search on the evaluated ResNet-50 dataset.

  • Scheduling targets bottleneck subgraphs

    Ansor's task scheduler allocates tuning time to subgraphs that are most likely to improve end-to-end DNN performance.

  • Hierarchy broadens search coverage

    Ansor's two-level sketch-and-annotation representation expands tensor-program search coverage beyond manual templates and early-pruned sequential construction.

  • bzip2 logs diverge sharply

    For bzip2 on Itanium, inlining logs split into a high-alignment group with similar decisions and a low-alignment group with substantially different callsite choices and no universally inlined callsite.

  • Constrained choices enable direct prediction

    Direct prediction of the best compiler option is practical for relatively small optimization problems and has produced measurable gains in loop unrolling and thread-coarsening studies.

  • Coupling maps become dynamic

    Distributed quantum compilers must model temporal coupling-map dynamics because remote operations are constrained by Bell-state availability, Bell-state regeneration, and classical communication latency.

  • Distributed QPUs cooperate virtually

    Distributed quantum computing can let remote quantum processing units cooperate as a virtual quantum processor for tasks that individual noisy intermediate-scale quantum devices cannot handle alone.

  • Distributed architectures require compilers

    Distributed quantum computing requires compilers that can map arbitrary quantum algorithms to distributed architectures while accounting for network and communication constraints.

  • Calibration guides gate thresholds

    Effective concentration calibration provides quantitative threshold choices that restore desired OR and AND gate behavior for unpurified seesaw components.

  • Entanglement swapping augments connectivity

    Entanglement swapping augments distributed-processor connectivity by enabling remote CNOTs between processors that are not directly connected by a quantum link, but it increases EPR-pair consumption at intermediate processors.

  • Experiments respect analytical bounds

    Experimental validation on medium-size quantum circuits respected the analytical bounds, and the data-qubit-swapping strategy generally required fewer link-generation layers and lower circuit depth than entanglement swapping alone.

  • Feature reduction preserves signal

    Feature selection and dimension reduction are necessary in compiler-learning problems because larger feature spaces require more training examples and can contain redundant information.

  • Open questions extend beyond optimization

    Future research in machine-learning compilation extends beyond choosing optimizations to mapping program and hardware spaces, learning analyses, discovering common features, and possibly learning better intermediate representations.

  • Entanglement strategy has linear bound

    In the worst-case topology, the entanglement-swapping-based strategy has per-layer depth overhead bounded by n/2 times a hardware-dependent constant des, where des equals cle plus cbsm plus ccx.

  • Slicing accelerates loop analysis

    Interprocedural slicing and polyhedral loop evaluation substantially reduce loop-analysis time for many benchmarks while preserving safe loop-bound analysis.

  • Metrics quantify decision variation

    Difference and alignment metrics quantify how much training-input selection changes compile-time optimization decisions by converting optimization logs into comparable decision vectors.

  • Empirical workflows improve compiler evidence

    Machine-learning-based compilation can make compiler optimization more evidence based because models must be grounded in empirical data that can be tested and independently scrutinized.

  • Learning guides compiler choices

    Machine-learning-based compilation can use a model inside the compiler to choose compiler heuristics or optimizations for a given program according to learned evidence about what makes code faster, smaller, or less power hungry.

  • Training data limits learning

    Machine-learning-based compiler optimization is limited by the quality, representativeness, and cost of its training data and cannot by itself create legal transformations or derive legality analyses.

  • Outliers disrupt gate composition

    Gate calibration can identify outlier unpurified components whose effective concentrations differ enough to disrupt multi-layer circuit composition.

  • Features encode program behavior

    Program features provide the quantifiable representation that allows learning algorithms to reason about source code, intermediate representation, runtime profiles, or combinations of those properties.

  • Remote CNOTs consume Bell states

    Remote CNOT execution consumes Bell-state resources and is limited by the number of available communication qubits, creating a tradeoff between communication capacity and data-qubit capacity.

  • Resubstitution fails reliable ranking

    Resubstitution does not reliably identify the best bzip2 FDO binary, indicating that ORC did not consistently turn more accurate same-input feedback into faster binaries in this study.

  • Complete programs improve tuning

    Sampling complete programs and then fine-tuning them with evolutionary search and a learned cost model avoids inaccurate estimates of incomplete programs.

  • Restoration compensates impurity

    Signal restoration and component tuning compensate for impurity in unpurified seesaw circuits, although leak reactions and sensitivity to synthesis and stoichiometry errors remain limiting concerns.

  • Single-input evaluation is unreliable

    Single-input performance evaluation of feedback-directed code transformations is unreliable because different evaluation inputs can prefer different training inputs.

  • WCEP governs WCET savings

    Static WCET reduction depends on optimizing the worst-case execution path, because reducing a noncritical path or a local block can leave the global WCET unchanged or only partly reduced.

  • Supervision maps features to decisions

    Supervised learning for compiler optimization learns correlations between program-feature values and the optimization decisions that produce optimal or near-optimal empirical performance.

  • Error model explains delay

    A model that represents synthesis errors in unpurified molecules predicts the slower 24-hour behavior of the rule 110-124 circuit better than the purified-circuit model.

  • Procedure shortens circuit building

    A three-step systematic procedure of calibration, outlier adjustment, and output tuning enabled construction of the rule 110 sub-circuit in three days.

  • Data swapping lowers asymptotic overhead

    The data-qubit-swapping-based strategy arranges data qubits so each CNOT in a layer operates on neighboring processors, and its compiled per-layer depth does not exceed n/4 dqs plus dqs prime.

  • Training precedes deployment

    The machine-learning compiler workflow separates model learning from deployment: training data is used to learn a model, and the learned model is then inserted into the compiler to make predictions for new programs.

  • Worst case maximizes overhead

    The paper's worst-case system model uses one data qubit per processor and a one-dimensional nearest-neighbor processor topology, making every CNOT remote and maximizing distributed-computation overhead.

  • Compiler complexity is polynomial

    The proposed compiler is computationally efficient because distributing a circuit has O(d n squared) complexity, with d the circuit depth and n the number of QPUs or logical qubits in the modeled worst case.

  • Optimizations compose strongly

    The WCC optimizations compose: applying register allocation, code and data scratchpad allocation, and procedure positioning to matmult reduces WCET by more than 70 percent relative to WCC -O2.

  • Thread coarsening is context dependent

    Thread coarsening decisions are context dependent because coarsening can improve instruction-level parallelism and memory behavior while also reducing parallelism or increasing register pressure on particular programs and hardware.

  • Training inputs affect FDO

    Training input selection affects both the compiler decisions made for feedback-directed inlining and if-conversion and the measured performance of the resulting binaries.

  • WCC integrates static analysis

    WCC couples a C compiler to the aiT static WCET analyzer so that WCET data is produced transparently during compilation rather than by a separate manual post-compilation step.

  • Back annotation enables optimization

    WCC’s back-annotation raises assembly-level WCET information to source-level ICD-C structures, enabling source-level optimizations to use WCET, WCEP membership, execution frequencies, cache misses, code size, and spill-code data.

  • Loop bounds become automatic

    WCC’s loop analyzer computes safe loop iteration bounds for most benchmark loops and exact bounds for the great majority, reducing reliance on manual flow facts.

  • Register allocation protects WCEP

    WCET-aware register allocation lowers WCET by avoiding spill code on the WCEP, even when this increases total spill code or text size outside the critical path.

  • Workloads exceed SPEC inputs

    The study's workloads extend beyond the standard SPEC CINT2000 inputs by adding representative application inputs, yielding 116 total inputs of which only 32 were provided by SPEC.

Comment Thread

Insightful24 points
Maya Santoro

What stands out to me is how the paper treats profiling as an extra pass over an already optimized program, rather than as a replacement for classic global optimization. That makes the 1.15 average speedup easier to interpret: the gains come from exposing hot-path structure that the baseline optimizer had already missed, not from skipping the normal compiler pipeline.

Insightful22 points
Eli Okafor

The weighted flow graph idea feels like the most durable part of the work. Once basic blocks and arcs carry execution counts, the compiler can stop pretending that all paths through a loop matter equally. Even if modern implementations would collect profiles differently, that representation-level move still explains why hot traces can justify different optimization choices.

Insightful25 points
Lina Kovac

I like the super-block construction, but the tail duplication tradeoff deserves as much attention as the speedup table. A single-entry region makes many transformations cleaner, yet copying code to get that shape is not free. The reported 1.07 average code growth sounds modest, though it still depends on the threshold and workload mix.

Insightful23 points
Rory Chen

The separate profiling and performance inputs are an important detail. Without that split, the results could mostly show that the compiler learned one exact run. Using different timing inputs makes the evaluation more credible, even though the benchmark set is still relatively small and centered on non-numeric C programs.

Insightful24 points
Samira Haddad

The profiling overhead is a reminder that this is a research prototype, not just a drop-in compiler flag. Runs that are 25 to 35 times slower would force users to choose profiling inputs carefully. Still, the paper's larger claim holds up: if you can afford representative profiles, classic optimizations become more targeted and sometimes more widely applicable.
