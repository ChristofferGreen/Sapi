WCC Compiler Reduces Worst-Case Execution Times

This source presents WCC, a C compiler framework designed to optimize hard real-time software for worst-case execution time rather than average-case speed. Its central idea is to integrate static WCET analysis into compilation, lift timing information across compiler abstraction levels, and use that information to drive source-level and assembly-level optimizations.

Overview and Commentary

Falk and Lokuciejewski frame WCC as a response to a practical real-time-systems problem: ordinary compilers optimize primarily for average-case behavior, while industrial real-time workflows often disable optimizations and perform WCET analysis only after code generation. The paper argues that this separation is both costly and technically weak, because WCET reduction depends on knowing the worst-case execution path and on understanding how local changes affect global timing. WCC therefore integrates the aiT static WCET analyzer into the compiler, translates low-level compiler IR into aiT’s CRL2 format, invokes aiT transparently, imports timing results, and back-annotates those results to source-level ICD-C structures. This infrastructure supports automated loop-bound analysis, source-level optimizations such as procedure cloning and positioning, and assembly-level optimizations such as scratchpad allocation and WCET-aware register allocation. The evidence base is largely benchmark-driven. The loop analyzer handles 707 loops across 96 benchmarks with 99% analyzability and 96% exactness, while slicing and polyhedral evaluation reduce analysis time sharply on selected examples. Procedure cloning can reduce WCET estimates dramatically when call contexts make loop bounds constant, though the paper is candid about code-size expansion. Procedure positioning improves cache behavior using WCET-derived call frequencies. ILP-based code and data scratchpad allocation reduce WCET by prioritizing regions and variables with high worst-case benefit. Register allocation avoids spill code on the WCEP and gives the largest average reduction among the reported individual optimizations. The final matmult experiment shows that several optimizations can compose, reducing WCET from 775,720 cycles to 227,794 cycles. The main limitation is that the results are tied to the WCC/TriCore/aiT environment and to benchmark suites, but the paper provides a coherent architecture and quantitative evidence for WCET-aware compilation as a system-level approach.

Section 01

Problem and Motivation

The paper’s motivating claim is that hard real-time development cannot rely on average-case compiler optimization or late manual timing checks. WCET reduction is path-sensitive: optimizing a block or a noncritical path may not reduce the global bound. This makes the compiler’s lack of timing knowledge a root cause rather than a minor tooling gap.

Section 02

Compiler-Analyzer Integration

WCC addresses the tooling gap by embedding aiT into compilation. The compiler converts its low-level representation into CRL2, invokes aiT without making the user manage analyzer setup, and imports value, loop-bound, cache, pipeline, and path-analysis results. This turns WCET analysis from a separate post-build activity into an optimization input.

Section 03

Back-Annotation as Bridge

A central architectural move is back-annotation from assembly-level structures to source-level ICD-C structures. The paper treats this mapping carefully because basic blocks do not always correspond one-to-one across IRs. Once mapped, WCC can expose WCEP membership, edge execution frequencies, cache misses, code size, and spill-code data to high-level transformations.

Claims Referencing This Source

  • Code SPM reduces WCET

    ILP-based code scratchpad allocation lowers WCET by moving beneficial basic-block regions into fast program scratchpad memory with negligible code-size and solver overhead.

  • Data SPM reduces WCET

    ILP-based data scratchpad allocation lowers WCET by moving frequently accessed variables into fast data scratchpad memory without changing generated code size.

  • Slicing accelerates loop analysis

    Interprocedural slicing and polyhedral loop evaluation substantially reduce loop-analysis time for many benchmarks while preserving safe loop-bound analysis.

  • WCEP governs WCET savings

    Static WCET reduction depends on optimizing the worst-case execution path, because reducing a noncritical path or a local block can leave the global WCET unchanged or only partly reduced.

  • Optimizations compose strongly

    The WCC optimizations compose: applying register allocation, code and data scratchpad allocation, and procedure positioning to matmult reduces WCET by more than 70 percent relative to WCC -O2.

  • WCC integrates static analysis

    WCC couples a C compiler to the aiT static WCET analyzer so that WCET data is produced transparently during compilation rather than by a separate manual post-compilation step.

  • Back annotation enables optimization

    WCC’s back-annotation raises assembly-level WCET information to source-level ICD-C structures, enabling source-level optimizations to use WCET, WCEP membership, execution frequencies, cache misses, code size, and spill-code data.

  • Loop bounds become automatic

    WCC’s loop analyzer computes safe loop iteration bounds for most benchmark loops and exact bounds for the great majority, reducing reliance on manual flow facts.

  • Cloning sharpens loop bounds

    WCET-aware procedure cloning improves WCET estimates by specializing functions whose data-dependent loop bounds become constant in cloned calling contexts, but it trades timing precision for code-size growth.

  • Register allocation protects WCEP

    WCET-aware register allocation lowers WCET by avoiding spill code on the WCEP, even when this increases total spill code or text size outside the critical path.

  • Positioning reduces cache misses

    WCET-centric procedure positioning reduces instruction-cache conflict misses by reordering functions using static WCET-derived call frequencies rather than profiling input data.
